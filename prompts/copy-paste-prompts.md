# Промпты для копипаста

Вставляй в AI-агента по ходу конвейера. Порядок - как в
[`../docs/00-pipeline-and-process.md`](../docs/00-pipeline-and-process.md).

Везде, где в квадратных скобках `[...]` - подставь своё.

---

## 0. Разворачивание инструмента под себя

Первый промпт, если ты взял готовый стартер. Агент настроит его под твои
реквизиты и твои документы.

```
Разверни для меня конструктор документов из папки starter/.

ШАГ 1 - МОИ РЕКВИЗИТЫ.
Они печатаются в КАЖДОМ документе и зашиваются в платёжный QR каждого счёта,
поэтому собираются один раз и аккуратно. Расспроси меня по списку:
полное и краткое наименование, ИНН, КПП (у ИП нет), ОГРН/ОГРНИП, юр. адрес,
банк, расчётный счёт, корр. счёт, БИК, e-mail, телефон, «в лице ...»
(родительный падеж), основание полномочий, должность для подписи, подпись
«Фамилия И.О.», отметка об НДС.

Спрашивай блоками по 3-4 поля, не по одному. Мои ответы сложи в JSON
и примени: `python setup.py --json <файл>.json`. Скрипт сам проверит
контрольные суммы ИНН, ОГРН и обоих счетов по БИК и скажет, если я опечатался.
Не выдумывай за меня ни одной цифры: чего не знаю - оставляем пустым.

ШАГ 2 - МОИ ДОКУМЕНТЫ.
Попроси меня положить в starter/references/ реальные подписанные документы,
которые я выпускаю руками (договор, при наличии - акт, доп.соглашение).
Прочитай каждый: `python read_etalon.py references/<файл>.docx`.
Напрямую .docx не читается - это zip с XML.

ШАГ 3 - СЛОВАРЬ ПОЛЕЙ.
По прочитанному собери словарь: что в документе меняется от сделки к сделке,
а что - неизменное тело. Покажи мне таблицей и дождись подтверждения.
Существующие поля стартера переиспользуй (их список: `python read_etalon.py
templates/dogovor_services.docx --placeholders`), новые заводи только там,
где в моём документе действительно есть чего-то нет в стартере.

ШАГ 4 - ШАБЛОН.
Собери шаблон СКРИПТОМ из моего эталона (не правь .docx руками - Word дробит
текст на runs, вписанный вручную плейсхолдер распадается). Тело документа
не меняй ни в одном символе. В конце скрипта - принудительная простановка
шрифта. Зарегистрируй тип в config/doc_types.yaml.

ШАГ 5 - ПРОВЕРКА.
Собери документ на моих данных, покажи мне файл и сверь с эталоном.
Напомни открыть его глазами: шрифт и вёрстку автопроверка не ловит.
```

## 1. День 0: разбор эталона и словарь полей

```
Ты помогаешь мне автоматизировать выпуск документов. Начинаем с разбора эталона.

Мой реальный [договор оказания услуг] лежит в starter/references/.

СНАЧАЛА прочитай его как текст: .docx - это zip с XML, напрямую он не читается.
Выполни `python read_etalon.py references/<файл>.docx` - получишь пронумерованные
абзацы и таблицы. Ссылайся дальше на номера абзацев.
(Если работаешь без стартера - извлеки текст через python-docx.)

Задача - НЕ переписывать его. Тело документа неприкосновенно.
Задача - понять, что в нём меняется от сделки к сделке.

1. Пройди по документу и раздели содержимое на два класса:
   ПЕРЕМЕННОЕ (меняется от сделки к сделке) и ПОСТОЯННОЕ (тело договора).
2. Из переменного собери СЛОВАРЬ ПОЛЕЙ таблицей: ключ (латиницей, snake_case) |
   человеческая метка | пример значения | обязательное ли.
3. Отдельно выпиши пограничные случаи: то, что выглядит переменным, но у меня
   может быть всегда одинаковым. По каждому спроси меня.
4. Не придумывай полей, которых нет в документе. Не хватает данных - спроси.

Не пиши код на этом шаге.
```

## 2. Сравнение нескольких эталонов

```
Прикладываю [два/три] моих реальных документа одного вида, но для разных
заказчиков.

Ответь на один вопрос: это ОДИН документ с разными реквизитами - или РАЗНЫЕ
документы?

1. Покажи содержательные различия таблицей: где расходятся формулировки,
   пункты, структура приложений. Различия только в реквизитах и суммах
   считай несущественными.
2. Дай вердикт: один шаблон с полями / два разных шаблона.
3. Если один - перечисли, какие различия уходят в поля.
4. Если два - объясни, какое именно структурное различие не сводится к полю.
```

## 3. Сборка шаблона из эталона

```
Собери шаблон .docx из моего эталона по словарю полей (прилагаю оба).

Требования:
1. Шаблон собирается СКРИПТОМ, который открывает эталон и переписывает нужные
   абзацы целиком. НЕ правь .docx руками: Word дробит текст на runs, вписанный
   вручную плейсхолдер распадается на куски и не подставится.
2. Тело документа не меняется ни в одном символе. Меняются только переменные
   места - на {{ ключ }} из словаря.
3. В конце скрипта - принудительная простановка шрифта по всему документу
   (параграфы, таблицы, колонтитулы). Иначе переписанные абзацы уедут
   в шрифт темы Office.
4. Списки (состав услуг, перечень работ) - циклом уровня абзаца, не переносами
   строк внутри абзаца.
5. После сборки покажи список плейсхолдеров - `python read_etalon.py
   templates/<шаблон>.docx --placeholders` - и сверь его со словарём полей:
   чего не хватает, что лишнее, нет ли опечатки в имени.
```

## 4. Контекст: форма → готовые строки

```
Напиши слой сборки контекста: форма → плоский словарь готовых строк для шаблона.

Принцип: в шаблон уезжают ГОТОВЫЕ СТРОКИ. Никакой логики внутри документа.
Всё умное - здесь, где это видно и тестируемо.

Нужно:
1. Даты в формате [«09» июня 2026 г.] - и календарная валидация: кривая дата
   должна падать с внятной ошибкой, а не подставлять мусор.
2. Суммы: целые рубли, разделитель тысяч - НЕРАЗРЫВНЫЙ пробел, сумма прописью.
3. Аванс и остаток с инвариантом «аванс + остаток == сумма договора» (остаток
   считается вычитанием, не вторым округлением).
4. Состав услуг: строки формы → пункты списка.
5. Чистые функции, без HTTP и без базы.

Потом накрой это golden-тестом: зафиксируй эталонный результат для одного
набора входных данных, чтобы любой рефактор доказывал свою безопасность сам.
```

## 5. Контрольные суммы и распознавание реквизитов

```
Добавь работу с реквизитами контрагента.

1. Контрольные суммы: ИНН (10 и 12 знаков), ОГРН/ОГРНИП, ключевание расчётного
   и корреспондентского счёта по БИК. Три состояния результата: сходится /
   не сходится / судить нельзя (не та длина - это НЕ ошибка).
2. Результат - ПРЕДУПРЕЖДЕНИЯ, не блокировка: бывают легальные исключения.
3. Парсер карточки предприятия: текст → поля. ДЕТЕРМИНИРОВАННЫЙ, на регулярках,
   без языковой модели - в юридическом документе цифру не должна «дорисовывать»
   модель.
4. Осторожно с двумя ловушками: альтернативу меток оборачивай в (?:...), иначе
   совпадёт голая метка без значения; расчётный и корреспондентский счета
   различай по префиксу (40… и 301…), иначе один затрёт другой.
5. Тесты обязательны: верное значение проходит, подменённая цифра не проходит.
```

## 6. Счёт, нумерация, платёжный QR

```
Добавь выпуск счёта.

1. Нумерация ГГГГММДДNNN, посуточный сброс. Механика peek/commit: номер
   узнаём, не тратя; расходуем ТОЛЬКО после того, как файл успешно собран.
   Проверка документа номер не тратит.
2. Счёт собирается из того же контекста, что и договор, плюс основание
   (№ и дата договора). Не собирай данные заново - разойдутся с договором.
3. Платёжный QR по ГОСТ Р 56042: сумма в копейках целым числом, разделитель |
   вычищается из значений, назначение платежа - короткая строка без «ёлочек»
   и «ё» (банковские приложения их не любят и режут длинные строки).
4. Конвертация в PDF локально, во временной папке с собственным профилем.

Отдельно напомни мне проверить QR телефоном - навести камеру и посмотреть,
что подставилось в платёжку.
```

## 7. Проверка результата

```
Напиши проверку ГОТОВОГО документа - того самого файла, который скачает
оператор, а не формы.

1. errors (отдавать нельзя): оставшиеся плейсхолдеры - в параграфах, ячейках
   таблиц И колонтитулах; пустые обязательные поля; сумма ≤ 0.
2. warnings (решает человек): контрольные суммы, пустой состав услуг.
3. Отдельно - проверка на ПРОПАВШИЕ значения: если имя поля в шаблоне
   разошлось с ключом контекста, подставится пустая строка и следа не будет.
   Возьми значения из формы и убедись, что они есть в тексте документа.
4. Без AI и без внешних вызовов.

И честно напиши в комментарии, чего эта проверка НЕ ловит: шрифт и вёрстку.
```

## 8. Приёмка отдельным свежим чатом

```
Ты принимаешь чужую работу. Я собрал конструктор документов, ты проверяешь
результат - не рассказ о процессе.

Прикладываю: эталон, готовый документ, словарь полей.

1. Сверь готовый документ с эталоном: расхождения в тексте, в структуре,
   в нумерации пунктов.
2. Проверь подстановку: все ли поля словаря видны в документе со своими
   значениями; нет ли пустых мест там, где ожидается значение.
3. Проверь оформление: шрифт по всему документу, таблицы не разъехались,
   документ помещается как задумано.
4. Проверь деньги: сумма цифрами и прописью совпадают, аванс плюс остаток
   равны сумме договора.
5. Ничего не чини сам. Верни список находок и вердикт: принимать /
   вернуть на доработку.
```

## 9. Новый тип документа

```
Добавь ещё один тип документа: [акт сверки].

Прикладываю эталон.

1. Сначала - словарь полей этого типа. Покажи, какие поля УЖЕ есть в системе,
   а какие новые. Существующие поля переиспользуй, не заводи синонимы.
2. Тип должен появиться в конфиге типов, а не в коде: шаблон + активные секции
   формы + дефолты.
3. Проверь, что старые типы не сломались: собери документ каждого типа и
   сверь с прошлой выгрузкой.
4. Напомни про disabled на скрытых секциях формы.
```
