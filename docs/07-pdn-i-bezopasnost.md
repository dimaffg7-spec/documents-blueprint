# 07. Персональные данные и безопасность

Конструктор документов по определению работает с чувствительным: реквизиты,
банковские счета, ФИО подписантов, суммы сделок. Это не «сайт-визитка», где
можно расслабиться.

> Ниже - инженерная практика, а не юридическая консультация. Требования
> к обработке персональных данных сверяй с действующим законодательством
> и с юристом.

## Опасная тройка

Аудит нужен, когда сходятся три вещи:

1. персональные данные;
2. данные третьих лиц (контрагентов);
3. отправка чего-либо наружу.

В этом конвейере первые две есть всегда. Значит, всё внимание - на третью.
Каждый исходящий вызов должен быть осознанным решением, а не побочным
эффектом библиотеки.

## Что не уходит наружу

- **Тела документов и реквизиты не отправляются во внешние API.** Ни в
  облачное распознавание, ни в LLM «на вычитку». Нужен OCR - ставится локально.
- **Конвертация в PDF - локальная** (LibreOffice на своей машине), не через
  онлайн-сервис.
- Если очень нужна LLM-вычитка - это отдельное решение с отдельным периметром
  и согласием контрагентов, а не «просто добавим ещё одну кнопку».

## Что не попадает в git

```gitignore
config/supplier.yaml      # свои реквизиты: расчётный счёт
config/contractors.md     # чужие реквизиты + ФИО подписантов
references/               # эталоны реальных договоров
data/                     # состояние нумерации
out/                      # готовые документы
```

В репозиторий идут только **примеры с нулями**. Проверять это нужно до первого
коммита, а не после: удалить файл из истории git на порядок сложнее, чем
не коммитить его.

**Особенно осторожно, если репозиторий когда-нибудь станет публичным.** Эталоны
договоров - это документы конкретных сторон, их нельзя выкладывать даже
«для примера».

## Периметр сервиса

Стартер слушает `127.0.0.1` - только эта машина. Так и задумано.

Локальный инструмент - это не «недоделанный продакшн», а осознанный выбор:
нет сервера, нет доступа снаружи, нет утечки. Для одного оператора этого более
чем достаточно.

Выставлять в сеть - отдельное решение, и тогда обязательны:

- **авторизация** на всех маршрутах, включая скачивание готовых файлов
  (иначе документ достаётся по прямой ссылке всякому, кто её угадал);
- **проверка прав на конкретный документ**, а не только «пользователь вошёл» -
  иначе один клиент увидит счёт другого, подставив чужой идентификатор;
- HTTPS, ограничение частоты запросов, журнал действий.

Пока операторов один, это можно отложить - но **записав как принятый риск**,
а не забыв.

## Журналы

В журнал действий пишется **что произошло**, а не **с какими данными**:
«создан счёт №..., оператор ..., сумма ...» - да; полный набор реквизитов
плательщика - нет. Журналы живут дольше, читаются шире и попадают в бэкапы
чаще, чем кажется.

## Удаление и анонимизация

Юридические документы не удаляются физически:

- ошибочный документ - **аннулируется** пометкой, а не стирается;
- запрос на удаление персональных данных закрывается **анонимизацией** -
  сущность остаётся, персональные поля обезличиваются. Иначе рассыпаются
  ссылки из связанных записей.

## Чек-лист перед первым коммитом

- [ ] `supplier.yaml` и база контрагентов - в `.gitignore`
- [ ] В репозитории только примеры с нулями
- [ ] Реальные эталоны договоров не в репозитории
- [ ] Ни один внешний вызов не получает реквизиты
- [ ] Сервис слушает локальный адрес
- [ ] Готовые документы не лежат в публичной папке
