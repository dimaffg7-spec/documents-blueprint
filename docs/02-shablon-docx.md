# 02. Шаблон .docx: как сделать и как не сломать

## Почему нельзя просто открыть Word и вписать плейсхолдеры

Можно. И в половине случаев это даже сработает. А в другой половине - нет,
и причина невидима.

Word хранит текст не строкой, а **последовательностью «runs»** - кусков
с одинаковым форматированием. Реальные документы, прошедшие через десяток
правок, раздроблены до неприличия: одно слово может состоять из четырёх runs,
иногда дробление идёт посимвольно (следы проверки орфографии, вставок,
копипаста из другого файла).

Что происходит, когда вписываешь `{{ customer_name }}` руками: символы
попадают в разные runs, и в XML документа это выглядит так:

```xml
<w:r><w:t>{{ cus</w:t></w:r><w:r><w:t>tomer_</w:t></w:r><w:r><w:t>name }}</w:t></w:r>
```

Библиотека подстановки ищет целую строку `{{ customer_name }}` и не находит её.
Плейсхолдер остаётся в готовом документе как есть. Хорошо, если заметишь.

## Правильный путь: build-скрипт

Шаблон собирается **скриптом из эталона**, а не правится руками:

1. скрипт открывает эталон;
2. находит нужный абзац **по тексту**, целиком;
3. **переписывает абзац начисто** - вместе с плейсхолдером;
4. в конце проставляет шрифт по всему документу.

Три выигрыша:

- **работает всегда** - переписанный абзац состоит из одного run;
- **повторяемо** - эталон обновился, прогнал скрипт заново;
- **видно в diff** - изменение шаблона перестаёт быть бинарным «файл поменялся».

Рабочий пример - [`../starter/build_demo_templates.py`](../starter/build_demo_templates.py).
Он собирает демо-шаблоны с нуля; для своего эталона логика та же, только
вместо `add_paragraph` - поиск абзаца и замена его содержимого.

## Обязательный шаг: шрифт

**Каждый переписанный абзац теряет шрифт.** Новый run без явного `rFonts`
берёт шрифт темы Office - обычно Calibri. Документ при этом проходит все
автоматические проверки: плейсхолдеров нет, поля на месте, суммы верные.
Просто он набран не тем шрифтом, чем весь остальной текст.

Такой баг живёт месяцами, потому что текстовые тесты его не видят - его видит
контрагент.

Поэтому `force_font(doc)` в конце любого build-скрипта - не опция, а часть
процедуры. И проверка выгрузки глазами - тоже.

## Таблицы: ширина колонок задаётся у таблицы, не у ячеек

Классический симптом: в Word таблица нормальная, а в PDF (LibreOffice) текст
сжался «в столбик» и уехал на вторую страницу.

Причина: при фиксированной раскладке рендерер берёт ширины из **грида
таблицы** (`tblGrid`/`gridCol`), а ширины отдельных ячеек игнорирует. Задал
только ячейки - грид остался равномерным.

Правило: ширины прописываются на уровне таблицы. И проверяются в том формате,
в котором документ реально уедет клиенту (обычно PDF).

## Логика в шаблоне: только структурная

Внутри шаблона допустим ровно один вид логики - **цикл по списку**:

```
{%p for item in services %}
{{ item }}
{%p endfor %}
```

Это про структуру документа (пунктов может быть три или семь), а не про
бизнес-правила.

Всё остальное - склонения, форматирование чисел, выбор формулировки по
условию - собирается **до** шаблона, в коде, и приезжает готовой строкой.
Причина простая: код видно, его можно накрыть тестом и посмотреть в diff.
Условие, спрятанное внутри .docx, не видит никто, включая тебя через полгода.

> Синтаксис `{%p ... %}` - тег уровня абзаца. Обычный `{% ... %}` внутри
> абзаца оставляет после себя пустые строки, а `\n` внутри run в Word вообще
> не перенос: текст слипнется в одну строку.

## Чек-лист готового шаблона

- [ ] Плейсхолдеры совпадают со словарём полей по именам, буква в букву
- [ ] Тело документа не изменилось относительно эталона (сверить диффом текста)
- [ ] Шрифт проставлен принудительно, проверен глазами
- [ ] Таблицы не разъезжаются в PDF
- [ ] Тестовый прогон: подставил данные - документ открывается в Word
