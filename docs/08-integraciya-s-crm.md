# 08. Встраивание в CRM или другую систему

Отдельный сервис с формой - это первый шаг. Второй: документ рождается там,
где живёт сделка, - по кнопке в карточке клиента, без повторного ввода данных.

Шаг делать не обязательно. Он окупается, когда сделок много и данные о них
уже где-то есть.

## Движок как stateless-рендерер

Правильная граница: **сервис документов ничего не помнит**.

```
CRM (данные, статусы, реестр)  →  движок (шаблон + подстановка)  →  файл
```

Все данные передаются явно в каждом запросе. Движок не ходит в базу CRM,
не хранит сделки, не знает про клиентов. Он умеет ровно одно: получил набор
полей - отдал документ.

Что это даёт:

- движок можно перезапустить, переехать, заменить - состояние не потеряется;
- его можно звать из чего угодно: из веб-формы, из бота, из скрипта;
- граница «кто хранит» / «кто рендерит» не размывается, а это главный источник
  каши в таких системах.

## Маппер: один слой, знающий про оба мира

Между доменом CRM и словарём движка стоит **маппер** - чистые функции без
HTTP и без базы:

```
сделка в CRM  →  [маппер]  →  плоский словарь полей  →  [HTTP-клиент]  →  движок
```

Маппер собирает готовые строки: даты в нужном формате, суммы прописью,
склонения, перечисления. Это тестируется без сервера и без базы - и должно
быть покрыто тестами, потому что именно здесь расходятся форматы.

Отдельный HTTP-клиент - единственное место, которое знает про адрес движка,
таймауты и коды ответа.

## Ошибки движка - три разных ответа оператору

Не сваливай всё в «ошибка 500». Оператору нужен следующий шаг:

| Ситуация | Что сказать |
|---|---|
| Сервис не отвечает (не запущен, упал) | «Сервис документов недоступен, попробуйте позже» |
| Движок отверг данные (прикладная ошибка) | показать причину: чего не хватает |
| Не прошла авторизация | «Проверьте токен» - чинить, а не повторять |

Три разных класса ошибок, потому что три разных действия. Иначе оператор
десять раз нажмёт «повторить» там, где надо было позвать администратора.

## Реестр на стороне CRM

Движок отдал файл - дальше система обязана помнить:

- номер и дату документа;
- **снимок реквизитов** на момент создания (см.
  [`05-rekvizity-i-kontragenty.md`](05-rekvizity-i-kontragenty.md));
- статус: черновик → сформирован → отправлен → подписан → аннулирован;
- ссылку на файл;
- **снимок формы целиком** - чтобы можно было пересобрать счёт или акт по тому
  же договору, ничего не вводя заново.

Снимок формы - не избыточность. Без него «выставить закрывающий счёт по
договору от марта» означает заполнить всё руками ещё раз, с риском разойтись
с договором.

## Инвариант, который легко потерять

Если система считает выручку или строит отчёты, следи за **двойным учётом**.

Типичный сценарий: оплата отмечается и на заказе, и на счёте - два независимых
реестра денег. Итог складывает оба, и месяц оказывается завышен ровно на сумму
тех сделок, где отметили и там, и там.

Лечится тем, что источник правды по деньгам - **один**, а второй реестр
на него ссылается. Решить это надо до того, как по цифрам примут решение.
