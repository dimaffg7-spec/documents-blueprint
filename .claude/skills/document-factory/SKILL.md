# document-factory - конструктор документов под ключ

Оркестратор. Ведёт сборку дисциплинированно, не пропуская слоёв. Полная
методология - в репозитории **documents-blueprint** (`docs/`, `prompts/`,
`templates/`, рабочий `starter/`). Если репозиторий доступен в проекте или
рядом - читай детали оттуда; если нет - следуй краткой версии ниже.

## Главный закон

**Подстановка, а не сочинение.** Тело документа неприкосновенно: оно прошло
через юриста и через подписание. Меняются только переменные поля.

Языковая модель НЕ пишет тело документа и НЕ правит формулировки. AI работает
в двух местах: помогает СОБРАТЬ конвейер (этап разработки) и распознаёт
реквизиты на входе. Причина: в подстановке ошибка видна, в сгенерированном
тексте - нет. Модель может уверенно поменять «не позднее 10 дней» на «в течение
10 дней», и это уже другое обязательство.

## Шаг 0 - классификация

Спроси, если неясно:

1. **Какие документы?** Список, а не «договоры вообще». Начинаем с одного -
   самого частого.
2. **Есть ли эталон** - реальный подписанный документ? Нет эталона - нет
   работы: типовую форму из интернета автоматизировать бессмысленно.
3. **Откуда данные?** Руками / карточка контрагента / уже есть в CRM.
4. **Сколько операторов?** Один - файловый счётчик и локальный сервис.
   Несколько - база с блокировкой и авторизация.

## Шаг 0.5 - если разворачиваем готовый стартер

Пользователь взял `starter/` и хочет рабочий инструмент под себя. Тогда до
всякой методологии собери две вещи, без которых он не поедет.

**Реквизиты владельца.** Печатаются в каждом документе и в QR каждого счёта.
Расспроси блоками по 3-4 поля (наименования, ИНН/КПП/ОГРН, адрес, банк и три
счёта, подписант, НДС), сложи в JSON и примени `python setup.py --json <файл>`.
Скрипт проверит контрольные суммы и скажет об опечатке. **Ни одной цифры
не выдумывай** - чего пользователь не знает, остаётся пустым. Пока
`config/supplier.yaml` не создан, форма честно светит плашкой «реквизиты
из примера, нули».

**Эталоны.** Попроси положить реальные документы в `starter/references/`
(папка в `.gitignore`) и прочитай каждый через `read_etalon.py`. Дальше -
обычный маршрут: словарь полей → шаблон скриптом → тип в `doc_types.yaml`.

Готовый промпт для пользователя - раздел 0 в `prompts/copy-paste-prompts.md`.

## Шаг 1 - День 0: эталон и словарь полей. БЕЗ КОДА

Это единственный шаг, который нельзя ускорить.

- **Сначала прочитай эталон как текст.** `.docx` — zip с XML, напрямую он не
  читается. Попроси положить файл в `starter/references/` (папка в `.gitignore`)
  и выполни `python read_etalon.py references/<файл>.docx` — получишь
  пронумерованные абзацы и таблицы. Ссылайся на номера абзацев, когда
  обсуждаешь, какое место документа становится полем. Если стартера рядом нет —
  извлеки текст любым способом (python-docx), но НЕ пытайся читать .docx как
  обычный файл и не проси пользователя «скопировать текст руками», пока не
  попробовал извлечь сам.
- Попроси приложить эталон (2-3, если есть). **Сравни их до сборки шаблона:**
  один документ с разными реквизитами или два разных? Ответ решает архитектуру.
- Раздели текст на переменное и постоянное. Собери словарь полей: ключ
  (snake_case) | метка | пример | обязательность.
- Пограничные случаи («выглядит переменным, но у меня всегда одинаково») -
  проговори с пользователем поимённо, не решай сам.
- **Один ключ - на всю систему:** шаблон, форма, база контрагентов, парсер,
  CRM. После первой рабочей версии не переименовывать.
- Регламентированную форму (утверждённый ведомством бланк) без реального
  образца НЕ делать вообще.

Шаблон брифа - `templates/brief-template.md`, пример словаря -
`templates/field-dictionary.example.md`.

## Шаг 2 - План фаз

Создай план по `templates/plan-phases.md`: 0 словарь → 1 один тип насквозь →
2 реквизиты → 3 второй тип → 4 счёт → 5 закрывающие → 6 проверка → 7 реестр.
У каждой фазы - критерий «готово», проверяемый руками.

Фазы 4-7 нужны не всем: юристу часто хватает 0-3.

## Шаг 3 - Ведение по слоям

**Шаблон.** Собирается СКРИПТОМ из эталона, не правится руками в Word: текст
раздроблен на runs, вписанный вручную плейсхолдер распадается и не подставится.
В конце скрипта - принудительная простановка шрифта (иначе Calibri вместо
основного шрифта, и это не ловится ни одним текстовым тестом). Ширины колонок
таблиц - на уровне таблицы, не ячеек. Логика в шаблоне только структурная -
цикл по списку, тегом уровня абзаца.

**Контекст.** В шаблон уезжают готовые строки. Даты с календарной валидацией,
суммы целыми рублями, разделитель тысяч - неразрывный пробел, сумма прописью
кодом. Инвариант: аванс + остаток == сумма договора (остаток вычитанием).

**Форма.** Скрытые секции прячутся ТОЛЬКО вместе с `disabled` - иначе поля
невидимой секции уезжают на сервер и перебивают активные, а `required` внутри
`display:none` молча блокирует отправку.

**Реквизиты.** Контрольные суммы ИНН / ОГРН / счетов по БИК - предупреждениями,
не блокировкой, с третьим состоянием «судить нельзя». Парсер карточки -
детерминированный, на регулярках. Реквизиты копируются в документ СНИМКОМ:
документ не должен плыть за карточкой контрагента.

**Счёт.** Нумерация ГГГГММДДNNN, peek/commit - номер расходуется только после
успешной сборки файла, проверка номер не тратит. QR по ГОСТ Р 56042: сумма
в копейках, разделитель `|` вычищен, назначение платежа короткое и без
типографики. Проверять QR телефоном, а не глазами.

**Проверка.** Открывает тот самый файл, который скачает оператор. errors
(плейсхолдеры, пустые обязательные, сумма ≤ 0) отдельно от warnings
(контрольные суммы). Отдельно - проверка на ПРОПАВШИЕ значения: разошлись
имена, и подставится пустая строка без всякой ошибки. Golden-тест на контекст.

## Шаг 4 - Финал

- Прогон на данных реальной прошлой сделки, сверка с эталоном.
- **Взгляд глазами обязателен**: шрифт, вёрстка, таблицы - в том формате,
  в котором документ уедет клиенту. «Нет плейсхолдеров» ≠ «документ готов».
- Приёмка отдельным свежим чатом (промпт 8 в `prompts/copy-paste-prompts.md`).
- Проверка периметра: реквизиты и эталоны не в git, наружу ничего не уходит.
- Новые грабли дописать в `docs/09-gotchas.md` - методология живая.

## Жёсткие правила

- **Тело документа не переписывать.** Ни «улучшить формулировку», ни «сделать
  юридически грамотнее». Только подстановка.
- **Не выдумывать реквизиты, суммы, номера, формулировки.** Нет данных -
  `[уточнить]` или вопрос пользователю.
- **Реквизиты и эталоны наружу не отправлять**: ни в облачный OCR, ни в LLM
  «на вычитку». Распознавание и конвертация - локально.
- **В git - только примеры с нулями.** `supplier.yaml`, база контрагентов,
  эталоны договоров, готовые документы - в `.gitignore` до первого коммита.
- **Документы не удаляются** - аннулируются пометкой.
- Дальше фазы 1 не идти, пока первый тип не собрался и не сверен с эталоном.

## Быстрый старт от рабочего кода

Если пользователю нужен результат сегодня, а не методология - в репозитории
есть `starter/`: работающий сервис (форма → .docx/PDF, контрольные суммы,
распознавание карточки, нумерация, QR, тесты). Запускается одной командой,
демо-шаблоны собираются скриптом. Дальше в него подставляется свой эталон
по `docs/02-shablon-docx.md`.
